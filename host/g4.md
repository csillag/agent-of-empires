# AoE builds on g4, g3 and g2: using and maintaining the remote build environment

**Since 2026-09-23 there are three identical build hosts: g4, g3 and g2.**
Each has the same chroot at `/srv/aoe-build/excalibur-arm64`, with its own
repo, target dir and job lock. g3 and g2 were cloned from g4's chroot (see
sec. 5, "Adding a build host"). `aoe-remote --host <node>` picks one host;
`aoe-remote --hosts g4,g3,g2` spreads the jobs over all three and runs them
at once (sec. 2). Everything below that says "g4" applies to each host.

LIVING document. Read this if you are responsible for building, linting or
testing agent-of-empires (AoE), or for keeping the build machine working.
The branch model, installing, deploying and restarting are covered in
`aoe-build-cookbook.md`. This file covers only where and how the compiling
happens.

Set up 2026-09-19. The scripts now live in this directory (`host/`), next to
`aoe-remote`. `~/local/bin/aoe-remote` points here. The copy under
`~/brain/scripts/aoe-remote-build/` is the old one; that tree is read-only.

## 1. The idea in one paragraph

superego (8 Cortex-A76 cores, 15 GB) takes about 18 minutes for an AoE
`dev-release` build and chokes the other agents doing it. g4 (a GB10 brain
cell: 20 cores, 121 GB) takes about 5.5 minutes. So AoE is compiled on g4, and
superego only sends commits and receives binaries and logs. The binary must
run on superego and link superego's distro C libraries (the kitchensink
carries the local-only `devendor-c-deps` branch). So the compile happens in a
**chroot on g4 whose toolchain, -dev libraries and glibc are exactly
superego's versions**. g4 itself runs Scutarius, which is newer than superego
and would produce binaries superego cannot load.

    superego                                   g4 (brain-cell-g4.lan)
    --------                                   ----------------------
    aoe-remote <sha> <jobs>
      | git push sha -> refs/jobs/<sha> -----> /srv/aoe-build/excalibur-arm64/home/csillag/aoe.git
      | ssh root: run-job <sha> <jobs> ------> flock job.lock; private mount ns; chroot as csillag
      |                                          job.sh: checkout, clean -ffdx, cargo/npm jobs
      | <---------------- log on stdout ------   (output streamed back into the log file)
      | scp out/aoe-<sha> <-------------------
      v
    ~/aoe-build/aoe-<sha8>, ~/aoe-build/remote-logs/<sha8>-<jobs>.log

## 2. Using it (the everyday part)

    aoe-remote [-C <repo>] <commit-ish> <job>...

`aoe-remote` is on PATH (`~/local/bin/aoe-remote` symlinks to
`~/brain/scripts/aoe-remote-build/aoe-remote`). It resolves `<commit-ish>` in
`~/local/src/agent-of-empires`, or in `<repo>` if you pass `-C`. Worktrees
share refs with the main repo, so a branch name from any worktree works.
**It builds the COMMIT, never a working tree.** Uncommitted changes are not
built. Commit first, even a throwaway WIP commit on a scratch branch.

| job | what runs inside the chroot (all under `umask 0022`, `LIBGIT2_NO_VENDOR=1`, `-j 20`) |
|---|---|
| `build` | `cargo build --profile dev-release --features web`, then the binary is copied back |
| `lint` | `cargo fmt --check`, then `cargo clippy --all-targets` |
| `libtest` | `cargo test --lib` (default dev profile) |
| `itest` | `npm ci` in `acp-worker/test-shim`, then `cargo test --features web --test integration` (dev profile ONLY: under dev-release 13 tests fail for profile reasons; see the cookbook) |
| `web` | in `web/`: `npm ci --ignore-scripts`, then `npm run format:check`, `npm run lint`, `npx tsc -b`, `npx vitest run`, `node tests/validate-coverage-matrix.mjs` |

**Parallel:** `aoe-remote --hosts g4,g3,g2 <sha> <job>...` assigns jobs longest
first to the least-loaded host (weights: libtest 540 s, build 320, itest 180,
lint 145, web 95) and runs one `run-job` per host concurrently. The logs are
`<sha8>-<jobs>@<host>.log`, one per host. The summary prints each host's
lines, and the exit code is 0 only if every job on every host passed. The
binary comes back from whichever host ran `build`. For a deploy, run the
kitchensink's full job set this way (cookbook: "run only the kitchensink").

Examples:

    aoe-remote --hosts g4,g3,g2 <sha> build lint libtest itest web   # deploy gate, parallel
    aoe-remote --host g3 <sha> lint                                  # one job on one host
    aoe-remote kitchensink build                          # just a binary
    aoe-remote fix/deploy-drain lint libtest itest        # branch checks
    aoe-remote 858a4c43 build lint libtest itest web      # everything, ~20-25 min

Every job runs even if an earlier one failed. The exit code is 0 only if all
of them passed.

**What you get back:**

- `~/aoe-build/aoe-<sha8>` (mode 0755) after a successful `build`. If that
  name already exists, the new binary goes to `~/aoe-build/aoe-<sha8>.remote`
  instead: a binary someone may be deploying from is never overwritten.
- `~/aoe-build/remote-logs/<sha8>-<job+job>.log`: the full output. Running
  the same sha with the same jobs again overwrites it.
- On stdout, a summary: every `=== STEP ... EXIT=n (secs)` and
  `=== JOB ... EXIT=n` line, the real `test result:` lines, error lines,
  failing test names, and after a build, `ldd` of the binary run ON
  SUPEREGO with a `distro C libs linked:` line. A de-vendored build must show
  `libgit2.so.1.9 libsqlite3.so.0 libssl.so.3 libcrypto.so.3 libzstd.so.1`.
  A topic branch without `devendor-c-deps` legitimately shows no sqlite; that
  is not a failure.

**Rules:**

- **It blocks for the whole run.** For anything longer than a build, launch
  it detached so a restart of your own worker cannot kill it:
  `setsid nohup aoe-remote <sha> <jobs> > /tmp/ar-<sha8>.out 2>&1 < /dev/null &`.
  Then wait on its pid with `kill -0`, never by matching its command line.
- **If the ssh connection dies, the job dies.** Nothing retries. Just run it
  again: the target dir is warm, so a rerun is cheap.
- **Jobs are serialized on g4.** A second caller prints
  `=== waiting for the running job to finish` and queues. Do not work around
  the lock: parallel cargo runs would share one target dir.
- **No `nice` is needed**, because g4 has no interactive users. superego only
  runs git, ssh and scp.
- **`aoe-remote` never installs anything.** `aoe-install`, `~/local/libexec`
  and daemon restarts stay manual, following the cookbook, and need the
  owner's go.
- The web job needs no browsers. `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1` is set
  and no Playwright tests run remotely. Owner rule: no prebuilt third-party
  binaries (rustup, Playwright browsers). Distro rustc, cargo and node only.
- `lint` and `libtest` run WITHOUT `--features web`. That matches the AoE
  expert's spec as of 2026-09-19. If you need the web-gated code linted, add
  a job; do not change these silently.

**Known test flakes** (they pass when rerun alone; they are not
environment problems): `acp_mcp` "record is JSON: EOF",
`session::smart_rename::...repo_aware...`,
`session::poller::test_poller_detects_change` under load, and
`acp_runner_control::runner_load_uses_requested_id_and_caches_response` (reads
the fake agent's log before its `session/cancel` line is written; seen once on
g2 on 2026-09-23, passed on rerun).
`tui::home::tests::archive_restart_grouping::tool_swap_test_restores_the_detect_as_registry`
("clobbered pre-existing alias zz-sentinel-test": a parallel test wrote the
shared profile config; seen once on g4 on 2026-09-23, passed on rerun).

**Measured timings (warm dependency cache):** build 325-335 s, fmt 6 s,
clippy 105-286 s, libtest 410-540 s (mostly compiling test code), itest
215-235 s, web about 90 s. Five jobs: 20-25 minutes.

## 3. Where everything lives

On **superego**:

| path | what |
|---|---|
| `~/brain/scripts/aoe-remote-build/aoe-remote` | the client (bash). Source of truth for all the scripts is this directory. |
| `.../job.sh`, `.../run-job` | the g4 side. **Every `aoe-remote` run re-deploys both** (copy to `.new`, then rename, so a job already running keeps its own copy). Edit them here, never on g4. |
| `.../rebuild-chroot`, `.../bootstrap-chroot` | rebuild the chroot (section 5) |
| `~/aoe-build/` | binaries (`aoe-<sha8>`) and `remote-logs/`. The AoE expert's deploy scripts also live here; leave them alone. |

On **g4**:

| path | what |
|---|---|
| `/srv/aoe-build/excalibur-arm64/` | the chroot (about 2.8 GB of system files) |
| `.../home/csillag/aoe.git` | bare repo; each job's sha lives at `refs/jobs/<sha>` |
| `.../home/csillag/src` | the one worktree, reset to the job's sha by `checkout -f` plus `clean -ffdx` |
| `.../home/csillag/target` | the one `CARGO_TARGET_DIR`: `debug/` for tests and clippy (about 21 GB), `dev-release/` for builds (about 2.4 GB) |
| `.../home/csillag/out/aoe-<sha>` | the last 5 built binaries; older ones are pruned |
| `.../home/csillag/{.cargo,.npm}` | crates.io and npm caches |
| `/srv/aoe-build/run-job` | the root-side entry point; `job.lock` is its lock |
| `/srv/aoe-build/superego-pins` | the pin file the chroot was built with |

One shared worktree and target dir is safe **because jobs are serialized and
always run in the same path**. The cookbook's "one target dir per worktree"
rule is about several worktrees sharing a target, which cannot happen here.

The chroot is entered only through `run-job`, inside `unshare -m` with its own
`/proc`, an rbind of `/dev`, and a fresh tmpfs on `/tmp` and `/dev/shm`. All
of those mounts vanish when the job ends, so **nothing stays mounted under the
chroot between jobs** and `rm -rf` of it is safe while no job runs. Commands
run as `csillag` (uid 1000) with a clean environment (`env -i`). The tests
need a non-root user: they isolate HOME and the tmux socket themselves.

Access: superego's csillag key reaches both `root@` and `csillag@`
`brain-cell-g4.lan`. The push goes to the chroot's bare repo as csillag@g4.
csillag@g4 is uid 1000 on the host too, so it owns the chroot's
`/home/csillag`. The g4 host has git and build-essential installed (owner's
request, 2026-09-19); the chroot has its own git.

## 4. Why the chroot looks the way it is

- **Devuan excalibur** because superego runs excalibur (glibc 2.41). A binary
  built against a newer glibc will not load on superego.
- **Plus selected packages from freia** (testing), because superego has them:
  rustc/cargo/rustfmt/clippy 1.95.0, libgit2 1.9.7, libsqlite3 3.53.4, npm 12,
  node 24.19. The kitchensink de-vendors libgit2, sqlite, openssl and zstd,
  so the **-dev versions must be superego's exactly**: the binary is compiled
  against those headers and links those sonames.
- **Pinning.** `/etc/apt/preferences.d/freia` keeps freia at priority 100
  (never chosen by default). `/etc/apt/preferences.d/superego-pins` pins
  every package whose superego version is NOT from excalibur to superego's
  exact version, at priority 1001. It has about 150 entries, generated from
  superego's `dpkg -l`. So `apt-get install X` inside the chroot yields
  superego's X or fails; it never silently yields a different version.
- **Repacked packages.** freia is a moving target. When superego's version
  leaves the mirror, the package is rebuilt from superego's installed files
  with `dpkg-repack` and installed from the .deb. As of 2026-09-19 that is
  `nodejs libnode137 libnode-dev libsimdutf33` (node 24.19.0). freia now has
  24.20, whose libnode needs glibc 2.43. Node does not link into aoe, but it
  builds the web bundle; the owner's rule is the same versions everywhere.
- **The keyring.** The `buildd` variant does not install devuan-keyring. The
  host's `/usr/share/keyrings/devuan-archive-keyring.gpg` is copied into the
  chroot's `trusted.gpg.d`, or apt rejects freia (`NO_PUBKEY 55C470D57732684B`).

Verify the match at any time:

    CHECK="rustc cargo rustfmt rust-clippy libgit2-dev libsqlite3-dev libssl-dev libzstd-dev libc6-dev nodejs npm tmux git"
    diff <(dpkg-query -W $CHECK | sort) \
         <(ssh root@brain-cell-g4.lan chroot /srv/aoe-build/excalibur-arm64 dpkg-query -W $CHECK | sort) \
      && echo match

The same check runs at the end of `rebuild-chroot`.

## 5. Maintenance

### Health check (under a minute)

    ssh root@brain-cell-g4.lan 'flock -n /srv/aoe-build/job.lock true && echo idle || echo busy; df -h / | tail -1;
        du -sh /srv/aoe-build/excalibur-arm64/home/csillag/target'

plus the version diff above. A real smoke test is `aoe-remote <some sha> build`.

### Disk

g4's root LV is 98 GB and is shared with other work on g4. Check the free
space first. The target dir only grows: every feature and profile combination
and every changed dependency adds to it.

- **Below about 20 GB free on g4 `/`**: delete `target/debug` under the job
  lock, so you never pull it out from under a running job:

      ssh root@brain-cell-g4.lan 'flock /srv/aoe-build/job.lock \
          rm -rf /srv/aoe-build/excalibur-arm64/home/csillag/target/debug'

  That costs one cold test compile (about +5 min). Deleting all of `target/`
  costs one cold build too.
- `out/` keeps 5 binaries (job.sh prunes it). `aoe.git` grows slowly with
  pushed history; `git gc` as csillag inside it if it ever matters.
- `.cargo/registry` and `.npm` are caches and can be deleted any time no job
  runs.

### When superego's toolchain or libraries change

Rebuild the chroot **before the next AoE build** after any change on
superego to rustc/cargo, the -dev libraries of libgit2, sqlite, openssl or
zstd, glibc, or node/npm. Otherwise the remote binary no longer matches
superego. The version diff above tells you whether you have to.

    ~/brain/scripts/aoe-remote-build/rebuild-chroot            # build .new beside the live one, verify
    ~/brain/scripts/aoe-remote-build/rebuild-chroot --swap     # same, then make it live

Run it detached (`setsid nohup ... > log 2>&1 &`): it takes 5-10 minutes, most
of it regenerating the pins on superego.

What it does:

1. Regenerates the pins from superego.
2. Repacks the `REPACK` list from superego.
3. Ships both to g4 and runs `bootstrap-chroot` there: mmdebstrap excalibur
   plus freia, the keyring, the pins, the packages, the csillag user, and an
   empty bare repo, all into `/srv/aoe-build/excalibur-arm64.new`.
4. Diffs the versions against superego and refuses to swap on any mismatch.

With `--swap` it waits for `job.lock`, moves the old chroot's `/home/csillag`
into the new one (repo, worktree, caches and target dir survive; cargo
rebuilds whatever a toolchain change invalidated), and replaces the live
chroot.

**If the install step fails** with "not installable" or "unmet dependencies",
a pinned superego version has left freia. Add that package, and any sibling
it pins exactly (as libnode137 is to nodejs), to `REPACK` in
`rebuild-chroot`, and run it again. `dpkg-repack` is not installed on
superego; the script downloads its .deb and runs it from a temp dir under
`fakeroot`. Nothing gets installed on superego.

**If a new package is needed for the build** (a new -dev library, a tool the
tests call), add it to `PKGS` in `rebuild-chroot` and to the `--include` list
or the install line in `bootstrap-chroot`. Then either rebuild, or for a quick
fix install it into the live chroot:

    ssh root@brain-cell-g4.lan 'chroot /srv/aoe-build/excalibur-arm64 apt-get install -y <pkg>'

The pins still apply, so you get superego's version. Put it in the scripts
too, or the next rebuild loses it.

### Adding or changing a job

Edit the `case` in `job.sh` (in brain, not on g4), keep the
`run <label> "<cmd>"` pattern so the STEP/JOB lines stay parseable, and commit
to brain. The next `aoe-remote` run deploys it. Tell the AoE agents in
`topics.log` when a job's meaning changes.

### Adding a build host

Clone g4's live chroot instead of bootstrapping a new one. freia moves, and
on 2026-09-23 a fresh `rebuild-chroot --host g3` failed on the npm chain:
freia's `node-glob` 13.0.6 breaks superego's pinned `node-jest-worker`
`-2`, which freia no longer carries. A clone is byte-identical to a chroot
that already builds, whatever freia does meanwhile.

1. On the new node, as root: `mkdir -p /srv/aoe-build` and
   `apt-get install --no-upgrade mmdebstrap git` (for later rebuilds). Dry-run
   the install first (`-s`): nothing kernel-, initramfs- or boot-related may
   come with it.
2. Stream the chroot from g4 under its job lock, without the target dir (a
   cold first build is cheaper than copying 32 GB):

       ssh root@brain-cell-g4.lan "cd /srv/aoe-build && flock job.lock tar --numeric-owner -cf - \
           --exclude=excalibur-arm64/home/csillag/target --exclude=excalibur-arm64/home/csillag/out \
           excalibur-arm64 | zstd -1 -T4 -q" \
         | ssh root@brain-cell-<node>.lan "cd /srv/aoe-build && zstd -dq | tar --numeric-owner -xpf -"

   17 GB took 2 minutes to two nodes at once (tee into both).
3. Run the version check against superego (sec. 4) for the new host.
4. Warm it: `aoe-remote --host <node> <kitchensink sha> build lint libtest itest web`.
   A cold run took about 30 minutes on g2 and g3.

`rebuild-chroot --host <node>` still exists and now creates `/srv/aoe-build` and
installs the host tools itself. It will hit the npm chain above until that
set is added to `REPACK`.

### When g4 is unavailable or gets reinstalled

- g4 powered off: `~/brain/scripts/braincell-power.sh on g4`. The fleet is
  shared: check `~/commissura/crew.md` and `fleet-placement-map.md` first.
  g4 is the Scutarius arm64 builder and test host too.
- g4 reinstalled: everything under `/srv/aoe-build` is gone. Recreate it:
  1. Check that superego can ssh to `root@` and `csillag@brain-cell-g4.lan`
     with BatchMode.
  2. Make sure the host has `mmdebstrap`, `rsync` and `zstd` (Scutarius
     has them), plus git.
  3. As root on g4: `mkdir -p /srv/aoe-build`.
  4. Run `rebuild-chroot --swap`. With no live chroot to carry a home over
     from, the new chroot's empty home and bare repo are used.
  5. The first build is cold: about 7 minutes, including crate downloads.
- **Fallback: build on superego**, per the cookbook's local recipe (`nice -n
  19`, `-j 6`, about 18 min). Only do that if g4 cannot be had.

### When superego moves to Scutarius

The owner plans it. Then superego and g4 run the same OS, and the chroot and
its pin and repack machinery have no reason to exist. Build natively on g4,
as a normal user in a plain directory, keeping `aoe-remote`'s interface
(sha plus jobs in, binary plus log out) so the agents' habits carry over.
Rewrite this document at that point.

## 6. Troubleshooting

| symptom | cause and fix |
|---|---|
| `git push to g4 failed` | ssh to csillag@g4 is broken, or `aoe.git` is missing or not owned by uid 1000. Check with `ssh csillag@brain-cell-g4.lan ls /srv/aoe-build/excalibur-arm64/home/csillag/aoe.git`. |
| `deploying job scripts to g4 failed` | ssh as root or as csillag is broken, or the chroot is missing |
| `=== waiting for the running job to finish` | another job holds `job.lock`; normal |
| `no such commit` | the commit-ish does not resolve in the repo; use `-C <worktree>`, or push or commit first |
| build OK but `LDD FAILED` on superego | the chroot no longer matches superego: run the version diff, then `rebuild-chroot` |
| `distro C libs linked:` lacks libsqlite3/libgit2 on a kitchensink sha | the commit lacks `devendor-c-deps`, or `LIBGIT2_NO_VENDOR` got lost in job.sh |
| `#[derive(RustEmbed)] folder '.../web/dist/' does not exist` | build.rs builds the web bundle only when web sources change, so a missing `web/dist` plus a cached build-script run gives this. job.sh keeps `web/dist` through the clean and touches `web/index.html` when it is missing; if you still see it, someone deleted it mid-job. Just rerun. |
| cargo "No space left on device" | g4 disk, see Disk |
| a job "passed" suspiciously fast after a manual edit on g4 | someone edited `src/` on g4 by hand; `clean -ffdx` plus `checkout -f` undo that on the next job. Never hand-edit on g4. |
| `COPY-BACK FAILED` | `out/aoe-<sha>` is missing on g4; look at the build step in the log |
| everything dies at once mid-run | the ssh session died (network, or your worker restarted); rerun detached |

## 7. Coordination

The g4 build environment is listed under whichever agent currently maintains
it, in `~/commissura/crew.md` (initially AoE Accelerator, aoe:beca59cf85c5).
Before rebuilding or swapping the chroot, deleting the target dir, or
rebooting g4, check that line and `topics.log`. A swap waits for `job.lock`,
but a reboot does not.
